# Version 2: setup and deployment

Version 2 is developed on `version-2`. The GitHub Actions → SSH → PM2 workflow now deploys only from `stagging`; `main` is reserved for Railway deployment, which is configured in Railway rather than this repository. The frontend remains on its separately configured hosting project.

## What changed

- Navigation is grouped into Daily work, Business and Team. Receipts, finances and reports link together; staff, attendance, leave and accounts link together.
- Help and the guided tour are available through the question mark in the top bar. The existing per-user/browser tour state prevents automatic repeats after skipping or completing the tour. Help can restart it.
- Required fields are marked and validation focuses the first invalid field, with inline guidance. Forms retain entered values after errors.
- Product creation asks for name, category, selling price, batch and expiry. Category defaults to Antibiotics, quantity defaults to zero and the low-stock threshold to ten. Supplier and barcode number are optional. Internal product codes are generated by the backend.
- A barcode number identifies a product and is entered as text, with optional camera or USB scanning. Batch/lot and expiry remain separate: different batches can share a barcode. Staff must choose a batch when a code matches several products.
- Sell items has one search/code input, a camera button, a visible cart and payment total, change calculation, and protected checkout retries. The amount due is the sum of item prices.
- Receipts use readable references such as `R-000123`. These derive from the sale ID, can be searched, and appear in printed receipts and exports. Historical database references remain intact and searchable.
- Leave and accounts share one searchable employee picker with keyboard navigation, active/unlinked filtering, and access to later result pages.
- Reports aggregate the entire selected period: sales totals, average sale, daily sales, top products and payment methods. Stock and staff reports are current snapshots. Report downloads contain full aggregate results; detail exports explicitly contain only the current page.
- Finances distinguish sales received, refunds, expenses and net recorded movement, with expense categories. This is not a bank balance or profit calculation.

## 1. Separate GitHub environment

Use the existing GitHub environment named **production** and its deployment secrets:

- `VPS_HOST`
- `VPS_USER`
- `VPS_PORT` (optional; defaults to 22)
- `VPS_SSH_KEY`

Branch selection in `.github/workflows/deploy.yml` is explicit:

| Branch | GitHub environment | Server directory | PM2 process |
| --- | --- | --- | --- |
| `stagging` | `production` | `~/metmma-backend` | `metmma-backend` |

Pushes to `stagging` and manual dispatches on `stagging` use this mapping. Other branches cannot run the deployment job. The workflow still uses the GitHub environment named `production` for its existing VPS secrets. Railway's deployment branch and trigger are managed in Railway project settings.

The `stagging` deployment replaces the code in the existing `~/metmma-backend` directory and reloads the existing `metmma-backend` PM2 process. The server `.env` is preserved during deployment, and concurrent deployments are serialized.

## 2. Neon database and server configuration

Keep the existing `~/metmma-backend/.env` on the VPS. If version 2 should use different database or frontend settings, update that file before deploying and restore the production values before deploying `main`:

The shared environment file should contain the appropriate values for the deployed branch:

```dotenv
NODE_ENV=production
PORT=3000
DATABASE_URL=postgresql://USER:PASSWORD@YOUR_NEON_HOST/neondb
MIGRATION_DATABASE_URL=postgresql://USER:PASSWORD@YOUR_DIRECT_NEON_HOST/neondb
DB_SSL=true
JWT_SECRET=YOUR_EXISTING_SECRET
ALLOWED_ORIGINS=https://your-frontend.example
TRUST_PROXY=1
PHARMACY_TIMEZONE=Africa/Blantyre
```

```sh
chmod 600 ~/metmma-backend/.env
```

Use the frontend origin configured for the deployed branch, without a trailing slash. As in the existing setup, omit `sslmode` and `channel_binding` parameters from URLs and let `DB_SSL=true` enforce certificate validation. `TRUST_PROXY=1` assumes one trusted reverse-proxy hop.

The workflow initializes only an empty public schema and runs the existing migrations. An existing database is preserved by initialization.

## 3. API domain and first deploy

Keep the existing API domain and reverse-proxy target for `~/metmma-backend`. Since both branches use the same PM2 process and port, version 2 does not have a separate API endpoint.

Commit and push the `version-2` branch after the environment and server `.env` are ready. The workflow will validate the code, package the backend with its SQL files, initialize/migrate the database and reload `metmma-backend`.

The API readiness check is:

```text
https://your-api.example/api/health
```

Expect `{"status":"OK"}`. A failed readiness check needs investigation before using the frontend.

## 4. First administrator

On the VPS, after migration:

```sh
cd ~/metmma-backend
export BOOTSTRAP_USERNAME=developer
read -rsp 'New administrator password (10–72 bytes): ' BOOTSTRAP_PASSWORD
echo
export BOOTSTRAP_PASSWORD
npm run bootstrap:admin
unset BOOTSTRAP_USERNAME BOOTSTRAP_PASSWORD
```

This command targets the shared `.env` and preserves existing valid accounts.

## 5. Separate Vercel project

Import the same repository into a new Vercel project and select `version-2` as its production branch:

- Root directory: `frontend`
- Build command: `npm run build`
- Output directory: `dist`
- Production variable: `VITE_API_BASE_URL=https://your-api.example`
- Frontend domain: your chosen frontend host, matching backend `ALLOWED_ORIGINS`

Redeploy after changing `VITE_API_BASE_URL`: Vite embeds it in the build. Do not assign the old frontend's domain to this project until you intend to switch versions.

## Acceptance checks after hosting

Use the configured database to check:

1. Sign in as the new administrator. Skip the tour; navigating and signing back in should not automatically reopen it. The question mark can restart it.
2. Add a product with only required details and without a supplier, barcode or internal code. Confirm generated code and default stock values. Test missing fields, invalid price and expiry errors.
3. Add the barcode number manually, by USB scanner, and by camera. Create a second batch with the same barcode and confirm checkout asks you to choose the correct batch.
4. Make a cash sale, verify change and print its short receipt. Find it by that reference. Verify a rejected checkout keeps its cart.
5. Record/edit/delete an expense and check totals, category breakdown and feedback. Open its associated receipt from income records.
6. Create staff and accounts; select a staff member through the single picker. Record leave with an optional reason blank. Test overlap and date errors.
7. Compare report totals against multiple pages of receipts, including a reversed sale. Download both a full report and a detail page and verify their stated scopes.
8. Check stock/staff report access with non-admin roles, and use a narrow mobile screen to check navigation and dialogs.

Database integration and hosted end-to-end verification are intentionally left for deployment at the user's request. Local syntax and production-build checks do not establish live workflow correctness.
